# 经验提示与名称模块的拆分复用评估

评估日期：2026-10-02，基于当时的 VTP 1.0.5 与 VP 配置。下文保留评估时的数据和候选建议。

**实施更新（2026-10-03，1.0.6）：** 用户最终选择将怪物并入扩展后的 `mob_names`，宝箱/桶及相关 VP 规则并入 `chest_names`；矿石 20 条与固定标签 4 条放入 VP `asm_main`，不新增 `ore_names`。`vault_xp` 已拆除。最终实现与安装要求见 [经验入口分工](vault-xp.md) 和 [宝箱模块](chest-names.md)，以下“建议/未实施”均指当时评估阶段。

用户补充：若不适合复用的内容较多，可以保留 vault_xp，并在文档中说明复用关系。判断依据应是经验模块自身的内容，而不是外部 VP 候选条目的数量。

## 结论与数据

建议以翻译对象组织共享模块，按调用入口提供适配。当前主要内容可复用，最终可以拆成怪物、宝箱、矿石三个模块，将四个固定标签交回 VP。暂未发现必须为大量独有译文继续维护独立 vault_xp 映射的理由。

| vault_xp 当前内容 | 条数 | 实查结果 | 建议去向 |
|---|---:|---|---|
| 怪物名 | 258 | 其中 235 条与 combat_stats 按实际格式化规则对应后逐值完全一致，无冲突；另 23 条为补充 | 合并成共享怪物名称模块 |
| 宝箱/桶完整名称 | 72 | 4 稀有度 × 9 类型 × 2 容器；与 VP 的类型、稀有度、容器显示词重叠，但不是 72 条同键映射 | 宝箱名称模块，共享词与组合逻辑，保留完整名称覆盖能力 |
| 矿石名 | 20 | 19 条取自资源包；Ore Funsoide 是英文占位 | 矿石显示模块，优先复用现有语言资源 |
| 固定标签 | 4 | Treasure Door、Coin Pile、Treasure Sand、Bonus | 在 handleDeltas 添加限定方法的 VP 静态规则 |

怪物直接重复占全部配置的 66.4%。宝箱另占 20.3%，属于可共享的命名结构，不能将其误报为已经存在的相同配置条目。预览只有一个固定名称，但与实战宝箱是同一语义，推荐随宝箱模块处理，不在 VP 再维护一份。

## 共享怪物名称模块

推荐名称 `mob_names`，由现有 `combat_stats` 扩展/迁移而来。两个 formatter 都有真实实体 ID，因此应使用现有的实体路径键约定，而不是从英文名称反推 ID：

- 结算：`CombatStatsContainerElement.formatMobName(String)`，参数为完整 ID 字符串。
- 经验：`ClientVaultXpTracker.formatMobName(ResourceLocation)`，将实际参数转为 ID，调用同一查表与回退入口。
- 沿用 `aggressive_cow` / `aggressive_cow_boss` 等区别，以及未配置时读取已注册实体语言译名、未知实体保留原结果的行为。
- 23 条补充应以基线具体实体 ID 和来源确认后合并。英文占位不能机械导入成强制覆盖值，否则可能挡住资源包已有的中文回退；不得由格式化显示名盲猜 ID。

VP 与其他显示入口的核查结果：

| 入口 | 观察 | 处理建议 |
|---|---|---|
| BountyHudModule.renderMockBounties 的 Zombie | 明确的僵尸预览字面量 | 可用已知 minecraft:zombie 接入同一表，仅迁移 Zombie 那一对，保留其余 HUD 文案 |
| GroupUtils.getEntityName 的具体实体分支 | 已从 NBT 实体 ID 取 EntityType 名称 Component | 若要求 VTP 自定义怪物译名在悬赏等界面一致，可在具体实体分支接入；保留 Component 格式与原回退 |
| GroupUtils.getEntityNamesAsString 及其 lambda | 具体实体和分组成员从 EntityType 取得语言名称 | 同属可扩展候选；实际迁移前检查调用方、排序与缓存，不全局替换 EntityType 的名称方法 |
| GroupUtils 的 Dweller；TextUtil 的 Horde、Tank 等 | 分组名，TextUtil 同组还有任务类型和维度名 | 不是具体实体名称；保持 VP，不能直接合并整个 TextUtil 规则 |
| Bestiary 两处 groupName 规则 | 含中文到英文的反向映射，涉及分类匹配 | 与上一组关联审查，不能只删一边或强行套实体表 |
| FighterEntity 的 Vault Dweller | VP 修改构造器的 lastName 初值；该字段还用于比较名称和更新皮肤 | 不直接合并。默认实体名、具体等级名、玩家/皮肤名字需区分；不能把“宝库居民”改成结算“宝库居民#1” |
| PetModelType / CompanionItemClient；ModDynamicModels$Armor 的 Zombie、Goat 等 | 宠物/装备外观名称，部分字面相同 | 语义不同，保留各自规则或以后独立命名模块 |

这意味着外部 VP 中不少“看起来是怪物名”的内容不宜合并，但不影响经验与结算这 235 条的明确复用。具名 NPC、玩家名和自定义名称也不应自动归入实体类型名称表。

## 共享宝箱名称模块

建议用 `chest_names` 承担完整语义，而不是只实现此前评估的 9 条 `chest_types`。后者可以作为前期步骤，但若长期并存两套类型词和完整名称表，重复问题仍然存在。

确认的接管范围：

| 入口 / VP 位置 | 当前内容 | 迁移边界 |
|---|---|---|
| VaultChestType.getName | main 中 9 对枚举显示名，实际修改 <clinit> 常量 | 在 getter 显示返回处查表，字段与枚举业务标识不改 |
| ClientVaultXpTracker.formatChestName | 稀有度、类型、桶标记组合 | 使用原枚举参数组合，避免读到已翻译 getName 后再反推英文 |
| createPreviewNotifications | Common Wooden Chest | 调用同一宝箱命名逻辑，保证改译后预览和实战同步 |
| VaultChestTileEntity.m_5446_ | main 中 4 对稀有度 + 32 对名称/拼接片段 | 仅接管构造显示 Component 的字符串；保留方块分支、上游回退及组件结构 |
| LootStatsContainerElement | getter 提供类型；另有 Barrel 后缀和 4 个稀有度统计标签 | 类型/桶命名及相关稀有度可共享；总 XP、陷阱、数量、说明句保留 VP |
| VaultChestIconElement | 4 个稀有度名及 Total/Trapped 等 | 只共享稀有度名，保留无关统计文本 |
| VaultAccessibilityScreen 的 Mname 规则 | 22 对枚举显示名，其中 7 个箱型与其余选项混合 | 只迁移经过类型确认的箱型显示读取，保留 COINS、OBJECTIVES 等其他选项；不修改 Enum.name 本身 |

建议配置维护 9 个类型词、4 个宝箱稀有度词，以及箱/桶/强化宝箱的名称格式；完整名称覆盖优先，供特殊译法或英文占位使用。格式应属于配置而不是把中文写进 Java。具体模板键及占位符校验属于实施前需要确定的配置约定，不能宣称已支持。

必须保留三个语义差异：

1. 类型名 Wooden 是“木制”，完整名称 Wooden Chest 是“木制宝箱”，不能用一个返回值混淆两者。
2. Strongbox 旧译文是“强化华丽宝箱”等，语序不能简单做类型词 + “强化宝箱”。
3. 宝箱实体方法的 Treasure Chest 分支会省略稀有度，而经验 formatter 仍拼接稀有度。共享词典不能改变两处原本不同的显示结构。

现有 20 条特殊桶组合仍是英文占位。若迁移，不能仅因类型词和 Barrel 已有中文就悄悄替换它们，应保留完整英文覆盖或作为待确认组合。装备稀有度、房间 Common/Omega 等不自动并入宝箱稀有度；语境相同且边界确认后才扩展。

宝箱实体显示方法可能在服务端生成标题，所以模块应支持两端通用查表，客户端专属入口仍按 CLIENT 注册。不能将客户端 I18n 引入服务端路径。

## 矿石显示模块

可保留独立 `ore_names`，但主要职责应是处理显示格式和必要覆盖，而不是复制资源包全部矿石译文。

- 经验 formatter 有真实 ResourceLocation，可检查注册表、读取对应现有语言译名，缺失时回退上游英文；如需自定义覆盖，应有明确优先级。
- 结算 LootStatsContainerElement 当前读取 ItemStack 显示名，再执行 `.replace(" - Vault Stone", "").replace("Ore", "")`；VP 还翻译了这两个去除片段。因而结算是短名，经验是完整名，不能简单让两个入口返回完全相同的字符串。
- 建议共享名称来源，分完整名与结算短名两个显示入口。前期保留结算行为，待确认资源包变体与短名规则后再迁移其字符串处理；不要使用无限制中文全局替换来生成短名。
- 第一轮 VP 扫描没有发现另一张与 vault_xp 20 条对应的完整矿石名表；主要重复来自现有资源包，而非 VP。不能为了合并而新建同内容副本。

如果配置改用方块完整 ID，这是新模块的特殊输入约定，实施前需确认；也可暂保留英文显示覆盖键，通过有来源的 ID 适配取得一致键。评估阶段不擅自更改此约定。

## 剩余文案与保留 vault_xp 的条件

四个固定标签可用一组静态 VP 规则定位 `ClientVaultXpTracker.handleDeltas`，只列 Treasure Door、Coin Pile、Treasure Sand、Bonus。Bonus 的英文占位继续保留或暂不覆盖。不能匹配/替换 `the_vault:coin_pile`、`the_vault:treasure_sand` 等 XP 查找 ID。

这一迁移需先移除 VTP 对这四个常量的钩子，并取消当前 vault_xp 对整个 Tracker 类的宽泛 VP 冲突判定；新模块应只拒绝自己接管的 formatter/预览规则，允许 handleDeltas 的 VP 规则共存。PRE_CLASS 在 VP 前执行，不代表可以忽略运行时值和双重翻译。

若实施中发现大量独有通知命名或短名规则暂时不宜统一，可保留 vault_xp 作为经验入口适配层：怪物调用共享怪物模块，宝箱/预览调用宝箱模块，矿石调用矿石模块，只有独有内容留在自己的配置。文档要列出每个入口的实际配置来源、回退和重载行为，不能只是注明“与其他表相同”却继续存两份映射。

当前架构将模块、配置文件和 runtime/transformer 注册关联，保留适配层时需明确是否还有独立配置；不能无用途地要求玩家安装空配置。现有 PatchModules 允许多个模块修改同一个类，但拒绝重复认领同一个方法：入口适配层与共享模块不能同时注入同一方法。

## 推荐实施顺序与验收

1. 先合并结算与经验怪物名，保留 ID 路径约定及语言回退；迁移工具必须保留用户自定义值，冲突生成报告，不以新英文占位覆盖旧中文。
2. 接管宝箱 getter、实体显示、经验/预览及确认过的 UI 片段，逐组移除 VP 旧规则并留接管说明；关联的动态 summary 规则要按调用位置审查，不能整组删除或放任二次翻译。
3. 矿石接入资源包名称；是否立即接管结算短名取决于变体审查结果。保留原显示细节比强行统一输出更重要。
4. 固定标签回 VP，评估 vault_xp 是否仍有独立职责。若全部转出，删除其运行注册和配置；若保留，文档明确复用来源。
