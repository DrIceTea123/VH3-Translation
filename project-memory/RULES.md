# 规则与约束快照

日期：2026-09-30。来源：初始对话中的明确需求及用户接受的方案。

## 明确用户要求

- R-001：翻译项目针对 Vault Hunters 3rd Edition，重点为 the_vault。
- R-002：必须随核心 mod 更新；可以为每个目标 JAR 发布专用版本，无需将跨版本通用兼容作为目标。
- R-003：the_vault 无源码，原始 JAR 是可用分析输入。
- R-004：`[PROGRAM]` 为主要工程，`origin-*` 为原始输入。
- R-005：保存每个独立对话中值得记录的规则、规范、需求、TODO及重要结论，供新对话读取。对项目记忆的日常维护已获持续授权。

## 已接受方案形成的工程约定

- R-006：渐进迁移；保留已有 VP 翻译，先用独立补丁解决高收益方法，不一次性重写数千条译文。
- R-007：开发时查看反编译代码，运行时做字节码转换；不把运行时反编译/编译引入玩家启动流程。
- R-008：优先方法级修改与可复用 Java 辅助方法；固定译文仍数据驱动。少数整类替换作为例外评估。
- R-009：保留业务 ID、存档键、网络字段及查找用内部名称，优先在显示边界翻译。
- R-010：目标方法签名、命中数量和变化应检查；已接受版本绑定不等于忽略上游逻辑变化。
- R-011：区分客户端显示与服务端文本。客户端 I18n 不得从专用服务端路径调用。
- R-012：原始输入保持原样，分析或修改产物放在明确的工作/工程位置。迁移后同一补丁位置避免由 VP 与新 mod 重复处理。

## 记录规范

- 当前明确用户指令可改变旧规则，写入有来源的修订记录；不能由助手建议静默改写用户要求。
- 方案、实查、推测、完成状态分开；未执行构建/游戏测试不得写“已验证可运行”。
- TODO 是待办清单，不是未来所有任务的自动执行授权。
- 只维护本项目共享记忆，不把其他项目约定自动引入此项目，也不修改全局记忆。
- 并发对话优先各写唯一增量文件，防止互相覆盖；快照归并必须保留来源与其他对话增量。
- PowerShell 对含方括号的工程路径使用 -LiteralPath。

## 尚未确定，不应擅自设定

- 新补丁 mod 的名称、modid、包名、工程位置和最终发布布局。
- 实际 Forge 精确版本、完整开发依赖和测试实例位置。
- 是否最终完全去除 VP；是否采用少量 Mixin 作为特殊实现工具。
- 是否创建 Git 仓库及提交策略；当前迁移没有对此做决定。
